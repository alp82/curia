# Multica (multica-ai/multica, "Multica, Inc.") — primary-source research

Date: 2026-07-24. Sources: repo `multica-ai/multica` cloned to scratch and read at commit **`b0bae3f`** ("docs(changelog): add v0.4.11 release entry", 2026-07-25 +0800, `origin/main`); in-repo docs (`apps/docs/content/docs/`, `README.md`, `LICENSE`, `SELF_HOSTING*.md`, `CLI_AND_DAEMON.md`); built-in worker skills (`server/internal/service/builtin_skills/`); SQL migrations (`server/migrations/`); https://multica.ai; GitHub API for stats, releases, and contributor distribution.

**Verdict: (b) — a design reference for [#33](https://github.com/alp82/curia/issues/33), not grounds to reopen [#17](https://github.com/alp82/curia/issues/17)/[#30](https://github.com/alp82/curia/issues/30).**

Multica is emphatically **not** vaporware and **not** a thin closed-core wrapper — it is the largest and most active candidate this map has examined (41.9k★, 219 contributors, 30 releases, v0.4.11 cut the day of this research), and its worker lane is real: 17 coding-tool backends as genuine Go subprocess adapters, per-ticket `git worktree` off a bare-repo cache, a daemon/server split with orphan recovery. But it fails curia's decisive filter for exactly the reason hermes and Paperclip did: **Multica's Postgres is the task list of record, and its GitHub integration is a read-only *pull-request* mirror with no Issues ingestion whatsoever.** The webhook handles `ping`, `installation`, `pull_request`, `check_suite`, `check_run`, `status` — there is no `issues` event, no issue importer, no octokit-equivalent write path, and the GitHub App is documented as **read-only by design** ("Multica never pushes commits, comments, or status checks back to GitHub"). The data flow is the inverse of curia's: Multica issues (`MUL-123`) are authoritative, and GitHub PRs link *back into* them. Adopting it recreates the two-writer drift [#9](https://github.com/alp82/curia/issues/9)/[#10](https://github.com/alp82/curia/issues/10) rejected.

It also misses on both remaining hard filters. **Attach is observe-only** — the WebSocket inbound frame handler accepts exactly `auth`, `subscribe`/`unsubscribe`, `ping` and silently drops everything else ([#12](https://github.com/alp82/curia/issues/12) fails). **There is no blocking human-ask primitive** — `AskUserQuestion` is *explicitly disabled* on the Claude lane, every backend is configured for autonomous auto-approval, and the task-status CHECK constraint has no human-waiting state; HITL is comment-then-end-turn-then-rewake, Paperclip's shape, not [#11](https://github.com/alp82/curia/issues/11)'s. **Discord does not exist as a bridge** (the only hits are a "join our community" sidebar card); Slack and Lark are the real chat surfaces. And the *"fully open source"* claim on the landing page is **false as stated** — the licence is a modified Apache-2.0 with a commercial-use restriction (§8).

What is worth stealing into [#33](https://github.com/alp82/curia/issues/33) is concrete and named in §9. One finding is a direct independent confirmation of a curia decision: Multica's source comment explains, in its own words, why `AskUserQuestion` cannot work in a headless stream-json worker — which is precisely why [#11](https://github.com/alp82/curia/issues/11) put `ask_human` on daemon-hosted MCP tools instead.

## 1. Provenance — real, large, company-backed, not Anthropic-adjacent

- **The repo is real and the marketing understates it.** `multica-ai/multica`, created **2026-01-13**, `pushed_at` 2026-07-24, **41,898★**, 5,302 forks, 1,176 open issues, 87 MB, Go primary. Not archived, not a fork, not a template.
- **219 contributors, but a clear company core**: top four (`Bohan-J` 1134, `NevilleQingNY` 1050, `forrestchang` 946, `ldnvnbl` 480) plus a bot (`multica-eve` 261) account for the overwhelming majority; the long tail is drive-by. This is a funded team's repo with community contributions, **not** bus-factor ~1 (contrast herdr, Paseo, Paperclip).
- **Shipping cadence is real**: 30 releases; **v0.4.11 published 2026-07-24**, carrying CLI (`multica_{linux,darwin,windows}_{amd64,arm64}`), a full Electron desktop app (`.dmg`/`.deb`/`.rpm`/`.AppImage`/`.exe`), and checksums. Homebrew tap (`multica-ai/homebrew-tap`) is live and was pushed the same day. Still **pre-1.0** (0.4.x).
- **Vendor**: `© 2025 Multica, Inc.` (LICENSE). The org has no website/email/location metadata set. Commit timezone is consistently `+0800`; the README's framing derives the name from **Multics** (time-sharing), and a `README.zh-CN.md` ships alongside the English one. The same org hosts `andrej-karpathy-skills` (196k★) — a viral `CLAUDE.md` repo that is plainly the top of their funnel.
- **The Anthropic-adjacent impression is false — killed explicitly.** There is **no** mention of Anthropic, affiliation, partnership, or trademark anywhere in `README.md`. Anthropic appears nowhere as a maintainer, sponsor, or org member. The impression comes only from Claude Code being the flagship supported backend (one of 17) and from the `andrej-karpathy-skills` halo. Multica, Inc. is an independent company; treat its Claude Code support exactly as you would Cline's or Paperclip's.
- **Not a thin wrapper**: `server/` is a substantial Go codebase (chi, pgx, sqlc-generated queries, 200+ migrations) with its own daemon, WebSocket hub, Redis relay, Prometheus metrics, and 17 hand-written agent adapters. The "14 supported coding tools" claim is real and **undercounts** — see §4.

## 2. What Multica actually is — verified

- **A server/daemon split.** The **server** (Go, chi, Postgres) owns issues, agents, squads, skills, and the task queue. The **daemon** runs on your machine, connects out to the server over WebSocket (`server/internal/daemonws/hub.go`), claims dispatched tasks, and spawns the coding-tool subprocess locally. This is how *"code never passes through Multica servers"* is structurally true — the claim holds for the self-host and local-daemon paths. (A `server/internal/cloudruntime/client.go` exists for hosted runtimes, where that claim would not apply.)
- **Self-host stack is genuinely small**: `docker-compose.selfhost.yml` is three services — `pgvector/pgvector:pg17`, `ghcr.io/multica-ai/multica-backend`, `ghcr.io/multica-ai/multica-web`. Redis is a dependency (`redis/go-redis/v9`, `server/internal/realtime/redis_relay.go`) used for multi-instance fan-out, not required for a single box. Docker Compose / single binary / Kubernetes claims are all backed by files in `deploy/` and `docker/`. Comfortable on an 8 GB Hetzner box.
- **The unit of work is a queued task bound to an issue.** `agent_task_queue` rows carry `agent_id`, `issue_id`, `status`, `priority`, `runtime_id`, `session_id`, `work_dir`, `trigger_comment_id`, `attempt`/`max_attempts`, `parent_task_id`, `squad_id`, `runtime_mcp_overlay`, `handoff_note`, and more (`server/pkg/db/generated/models.go`).
- **Agents are DB rows with profiles**, assigned issues like colleagues; **Squads** add a leader agent that delegates to members (`EnqueueTaskForSquadLeader`, `server/internal/service/task.go:566`); **Autopilots** are the cron/trigger layer (`robfig/cron/v3`, `server/internal/service/autopilot.go`).

## 3. State home — the decisive filter, and Multica fails it

- **Issues live in Multica's Postgres, addressed by workspace-prefixed keys** (`MUL-123`). Statuses: `backlog | todo | in_progress | in_review | blocked | done | cancelled`. Sub-issues, parents, stages, assignees, metadata, and typed custom properties are all Multica-owned (`server/internal/service/builtin_skills/multica-working-on-issues/SKILL.md`).
- **The GitHub integration is PR-mirroring only, and read-only by design.** From `apps/docs/content/docs/github-integration.mdx`: the GitHub App requests **read-only** access to pull requests, checks, commit statuses, and metadata, and *"Multica never pushes commits, comments, or status checks back to GitHub."* It creates three tables — `github_installation`, `github_pull_request`, `issue_pull_request` (migration `079_github_integration`).
- **No GitHub Issues ingestion exists.** The webhook dispatch switch (`server/internal/handler/github.go:797-807`) handles exactly: `ping`, `installation`, `pull_request`, `check_suite`, `check_run`, `status`. There is **no `issues` case, no `issue_comment` case**. The Go server has **no GitHub API client dependency at all** in `go.mod` — no `go-github`. The only outbound GitHub calls are one hand-rolled GraphQL query in `server/internal/integrations/ghsnapshot/`, whose entire body is `repository → pullRequest → { mergeable, commits(last:1) → statusCheckRollup }` (`snapshot.go:22-30`) — CI rollup and merge-conflict state for the PR card, nothing else.
- **The flow is the inverse of curia's.** A PR whose branch/title/body contains `MUL-123` auto-links to *Multica's* issue; `Closes MUL-123` records close intent and merging advances *Multica's* issue to `done`. GitHub is the code host; Multica is the tracker. Other VCS providers (`forgejo`, `gitea`, `gitlab`) are supported on the same PR-mirror basis (`server/internal/handler/vcs_webhook.go`).
- **Consequence for curia:** the best available on-ramp is `POST /api/webhooks/autopilots/{token}` — an external system fires an autopilot which creates a *Multica* issue and assigns a Multica agent. That is a **mirror**, i.e. the exact two-writer drift [#9](https://github.com/alp82/curia/issues/9)/[#10](https://github.com/alp82/curia/issues/10) disqualified hermes' SQLite kanban for, now with 200+ migrations behind it. **There is no configuration in which the GitHub frontier drives Multica and GitHub stays the single source of truth.**
- Nothing on the roadmap or in the docs suggests otherwise; unlike Paperclip, Multica does not even list bring-your-own-tracker as a future item.

## 4. Worker lane — the strongest part, and the closest to curia's own conclusions

- **17 backends, not 14** (`server/pkg/agent/agent.go:225`, `SupportedTypes`): `claude`, `codebuddy`, `codex`, `copilot`, `opencode`, `deveco`, `openclaw`, `hermes`, `pi`, `cursor`, `kimi`, `kiro`, `antigravity`, `qoder`, `traecli`, `grok`, `qwen`. Each is a hand-written Go adapter (`claude.go`, `codex.go`, `cursor.go`, …) with its own stream parser, arg allow/block list, model list, and error taxonomy. The landing page's list of 14 is a stale subset. **`hermes` and `pi` — two of curia's own evaluated candidates — are both first-class backends here.**
- **Real subprocesses, mixed protocols.** Claude Code is driven over **stream-json, not PTY and not ACP**: `claude -p --output-format stream-json --input-format stream-json --verbose --permission-mode bypassPermissions --disallowedTools AskUserQuestion` (`server/pkg/agent/claude.go:610-622`), plus `--model`, `--effort`, `--max-turns`, `--append-system-prompt`, `--resume <session>`, `--mcp-config`, `--strict-mcp-config`, `--settings`. This is the same lane Paseo used and that [#29](https://github.com/alp82/curia/issues/29) found dodges terminal-only first-spawn dialogs. Others differ: `kiro` and `grok` are ACP (`session/new`, `session/update`); `qwen` is native stream-json; `codex` uses its app-server protocol.
- **Per-ticket `git worktree` — matches [#30](https://github.com/alp82/curia/issues/30) exactly.** The daemon keeps a **bare repo cache** per repository and cuts a worktree per task, with a GC that runs `git worktree prune` and scans stale branches (`server/internal/daemon/gc.go:729-854`). A `local_directory` mode exists for running in-place in a user directory instead (`server/internal/daemon/local_directory.go`).
- **Per-spawn env: yes.** `cmd.Env = buildEnv(b.cfg.Env)` (`claude.go:67`); agents carry `custom_env`; a `runtime_mcp_overlay` jsonb column holds **per-task MCP servers computed at dispatch time, merged on top of `agent.mcp_config`, and cleared after the task completes via a DB trigger** (`server/pkg/db/generated/models.go:125`).
- **Per-worker `CLAUDE_CONFIG_DIR` ([#29](https://github.com/alp82/curia/issues/29)): NOT provided — and this is a real gap.** `CLAUDE_CONFIG_DIR` has **zero occurrences repo-wide**. Multica *does* isolate three other lanes — a per-task `CODEX_HOME` seeded from `~/.codex` (`execenv.go:344`, `hydrateCodexSkills`), a per-task `HERMES_HOME` overlay (`:372`), and a per-task `CURSOR_DATA_DIR` for the approvals sidecar (`:387`) — but the source states the rule plainly: *"Codex is the only runtime that needs this two-stage hydration because the daemon sets CODEX_HOME to a per-task directory… **Other runtimes leave HOME untouched and discover user-level skills natively**"* (`execenv.go:682-684`). Claude Code workers therefore read the host's real `~/.claude` — settings, skills, and plugins (`server/internal/daemon/claude_plugins.go:39-48`, `local_skills.go:130`). This is the exact host-config-inheritance footgun curia hit in [#23](https://github.com/alp82/curia/issues/23)/[#24](https://github.com/alp82/curia/issues/24)/[#26](https://github.com/alp82/curia/issues/26) and made mandatory to fix in [#29](https://github.com/alp82/curia/issues/29). Multica has not solved it on the Claude lane.
- **Model/backend per task: partial.** `--model` and `--effort` are per-agent settings (thinking level, model list per backend) rather than per-*task* overrides; the per-task override surface is the MCP overlay and handoff note. Curia's [#13](https://github.com/alp82/curia/issues/13) label-driven per-ticket model choice would need the agent row swapped, not a field set.

## 5. Skills — same format, zero migration cost

- **Multica uses standard `SKILL.md` with YAML frontmatter** (`server/internal/skill/frontmatter.go`, `reserved.go:12` `ContentFilename = "SKILL.md"`), including `name`, `description`, `user-invocable`, and `allowed-tools` — byte-for-byte the Claude-Code/Agent-Skills grammar. The repo even carries its own `.agents/skills/web-design-guidelines/SKILL.md`.
- **It is a superset, not a competitor.** Workspace skills are stored in Postgres and materialised to disk per task; **user-level skills are discovered natively from `~/.claude/skills`** on the Claude lane (`local_skills.go:130`), with per-provider roots for Codex/Kiro/etc. Skill import from an archive is supported (`skill_import_archive.go`).
- **Answer to the ticket's question: curia's existing skills port as-is.** There is no competing format and no migration cost. This is the one axis where Multica is unambiguously compatible.

## 6. Escalation (HITL) — durable, but end-turn, and with no Discord

- **There is no blocking human-ask primitive.** The task-status CHECK constraint is `queued | dispatched | running | completed | failed | cancelled | waiting_local_directory | deferred` (`migrations/001_init.up.sql:132`, widened by `109` and `128`). The only "waiting" state waits for a **local directory**, not a human. Nothing corresponds to curia's worker-blocked-in-`ask_human`.
- **Every backend is configured for autonomous auto-approval**: Claude `--permission-mode bypassPermissions`; Cursor `--yolo` (`cursor.go:823`, commented *"auto-approval for autonomous operation"*); Codex `approvalPolicy: nil` / `approval_policy = "never"`; Grok `--always-approve`; CodeBuddy opens stdin for *"control_request auto-approval"*. Permission gates are systematically disabled by design — the opposite of a HITL surface.
- **`AskUserQuestion` is explicitly disallowed, and the reason is a direct confirmation of curia's [#11](https://github.com/alp82/curia/issues/11) design.** From `claude.go:615-622`: *"AskUserQuestion is Claude Code's built-in interactive question tool. The daemon runs Claude in non-interactive stream-json mode and has no UI for the prompt to render in, so a call returns an empty answer and the agent ends up 'inferring' silently — the user never sees the question (see GitHub #2588). **User-facing clarification belongs in an issue comment instead.**"* Multica independently hit the failure mode curia avoided by putting `ask_human` on daemon-hosted MCP tools with a real rendering surface.
- **HITL is therefore: comment → end turn → human replies → re-wake.** A human (or agent) comment re-enqueues the agent via `EnqueueTaskForMention` / `EnqueueTaskForThreadParent` (`task.go:1062-1068`). It is fully **durable** — everything is Postgres rows, so a restart loses nothing — but it is Paperclip's shape, not curia's blocking contract. Recommended state is parked in issue metadata keys (`waiting_on`, `blocked_reason`).
- **"Escalation" in the schema is agent-to-agent, not human.** `escalation_for_task_id` + `fire_at` + status `deferred` (`migrations/128_comment_routing_escalation.up.sql`) implement a **deferred assignee fallback**: if a mentioned agent doesn't handle a routed comment, it escalates to the issue assignee after a delay (`EnqueueDeferredAssigneeFallback`, `task.go:1170`). Useful pattern, wrong axis.
- **Discord: does not exist as a bridge.** No Discord library in `go.mod`; every hit is a community-invite card (`packages/views/layout/join-discord-card.tsx`, `discord.tsx`, landing-page i18n strings). **Telegram: zero.** The real chat surfaces are **Slack** (`slack-go/slack`; full `inbound.go`/`outbound.go`/`replier.go`/`channel.go`/BYO-install) and **Lark/Feishu** (`server/internal/integrations/lark/`, with a careful WebSocket connector). Email via `resend-go`. For curia this is a total miss — [#31](https://github.com/alp82/curia/issues/31)'s Discord bridge is already built and verified live against a mid-escalation reboot.
- **Images into the worker: structurally impossible on the Claude lane.** `buildClaudeInput` marshals `content: []map[string]string{{"type":"text","text":prompt}}` (`claude.go:681-690`) — a `map[string]string` **cannot** express an image block's nested `source` object. Curia's [#12](https://github.com/alp82/curia/issues/12) images-both-ways requirement fails without a code change, the same way it failed for Cline ([#28](https://github.com/alp82/curia/issues/28)).

## 7. Attach — observe-only, confirmed twice

- **The web WebSocket does not accept input.** `server/internal/realtime/hub.go`: the first frame must be `{"type":"auth"}` (`firstMessageAuth:702-723`); thereafter `handleFrame` switches on exactly `subscribe`, `unsubscribe`, `ping` — and the `default` branch logs *"ws inbound: unknown frame"* and returns (`:878-912`). There is no message, steer, interject, or input frame. Multi-client **watching** is real (workspace-scoped hub with a Redis relay for multi-instance fan-out); **injecting into a running turn is impossible**.
- **The agent's stdin stays open, but not for humans.** `claude.go:116-118` keeps stdin open after the initial user message with the comment *"Claude's stream-json protocol sends control_response frames on the same input stream; closing stdin here [would break that]"* — the writes are `handleControlRequest` responses (`:380-419`), the SDK control protocol. Not a steering channel. Repo-wide there is no steering/interjection path; a mid-turn comment lands as a row and wakes the *next* run.
- **Phone surface exists but is a board, not a terminal.** `apps/mobile` is a real Expo/React Native app (`@multica/mobile`, expo-router) — issues, comments, notifications. Comparable in role to curia's Discord surface, not to [#32](https://github.com/alp82/curia/issues/32)'s ttyd terminal attach. There is no PTY anywhere in the product.
- **Restart survival is well-engineered but re-dispatch-shaped**, matching curia's posture: the daemon reconnects over WebSocket, re-registers, and calls **recover-orphans** to reconcile rows left `dispatched`/`running`/`waiting_local_directory` (`daemon.go:892-902`, `:1814`), with HTTP heartbeats as the fallback when the WS is flaky (`:989`). This is close to the **orphan sweep** [#19](https://github.com/alp82/curia/issues/19) said curia's daemon would need.

## 8. Licence, telemetry, self-host — where the marketing overstates

- **"Fully open source" is false as stated.** `LICENSE` is headed *"Open Source License"* but reads: *"Multica is licensed under a **modified version of the Apache License 2.0**, with the following additional conditions"* — (a) you may **not** use the source to provide a hosted service to third parties or embed it in a commercially distributed product without a commercial licence from the producer; (b) you may **not** remove or modify the LOGO or copyright information in `apps/web/` or the `web` Docker image. This is the Dify-style source-available licence; GitHub's own classifier reports **`NOASSERTION`**, i.e. it is not a recognised OSI licence. The landing page's *"Multica is fully open source"* and *"Inspect every line, self-host on your own terms"* are only half-right: inspection and self-hosting are genuinely permitted, the "open source" label is not earned.
- **For curia specifically, the licence is not a blocker**: *"Internal use within a single organization (including multiple workspaces) does not require a commercial license."* Alp self-hosting on his own Hetzner box for his own projects is squarely inside the grant.
- **But clause 2(a) is a standing risk**: *"The producer can adjust the open-source agreement to be more strict or relaxed as deemed necessary"* — contributors pre-agree to unilateral licence tightening, and 2(b) pre-assigns commercial use of contributions. No OpenACP-style repo-vs-published-artifact split was found (the tarballs are the same modified-Apache code), but the licence can change under you by design.
- **Telemetry — docs and source disagree, in the safe direction.** `apps/docs/content/docs/environment-variables.mdx:279-282` says *"By default, the server reports to Multica's official PostHog instance"* with `POSTHOG_API_KEY` defaulting to a *"built-in default key."* **Source contradicts this for a from-source build**: `server/internal/analytics/client.go:78-80` falls back to a **no-op client** when `POSTHOG_API_KEY` is empty, and no `phc_*` key is committed anywhere in the repo, Dockerfiles, or compose files. So building from this repo = telemetry off; the published `ghcr.io` images presumably bake a key in CI (unverifiable from source). `ANALYTICS_DISABLED=true` force-disables either way. Set it regardless.
- **Self-host claims otherwise check out**: Docker Compose / single binary / Kubernetes are all real, and the local-daemon architecture makes *"code never passes through Multica servers"* structurally true for the self-host path.

## 9. Verdict and what to borrow into [#33](https://github.com/alp82/curia/issues/33)

**(b) Design reference. [#17](https://github.com/alp82/curia/issues/17) and [#30](https://github.com/alp82/curia/issues/30) stand — nothing here reopens them.**

Against the three hard filters this map has accumulated, Multica scores 0/3: **state home** — its Postgres owns tasks and there is no GitHub Issues ingestion at all, only a read-only PR mirror (§3); **attach** — WebSocket inbound accepts only subscribe/ping, no injection into a live turn (§7); **escalation** — no blocking `ask_human`, no human-wait task state, all backends set to auto-approve, no Discord, and images structurally impossible into the Claude worker (§6). It additionally fails the mandatory per-worker `CLAUDE_CONFIG_DIR` from [#29](https://github.com/alp82/curia/issues/29) on the Claude lane specifically (§4). No part of the built [#31](https://github.com/alp82/curia/issues/31) bridge would be rebuilt or discarded on account of this evaluation.

The shape it *does* share with curia — daemon dispatching fresh per-ticket workers into git worktrees across many coding tools — is the same shape curia already chose in [#9](https://github.com/alp82/curia/issues/9)/[#30](https://github.com/alp82/curia/issues/30). Multica is a well-built confirmation that the architecture is right, wrapped around a tracker curia cannot adopt.

Worth borrowing, concretely:

1. **Bare-repo cache + per-task worktree, with a real GC.** `git worktree prune` plus a stale-branch scan over every cached bare repo (`daemon/gc.go:729-854`) — [#30](https://github.com/alp82/curia/issues/30) decided the worktree model but not its reaping; this is the missing half.
2. **Reconnect → re-register → recover-orphans.** The daemon treats a WebSocket reconnect as a reconciliation trigger and proactively deregisters orphaned server-side rows (`daemon.go:892-902`, `:1814`), with HTTP heartbeats as a starvation guard (`:287`). Directly applicable to the orphan sweep [#19](https://github.com/alp82/curia/issues/19) required.
3. **Per-task MCP overlay, auto-cleared.** A `runtime_mcp_overlay` jsonb computed at dispatch, merged over the agent's base MCP config, and **cleared by a DB trigger when the task completes**. Curia's daemon-hosted `ask_human`/`notify` MCP servers ([#11](https://github.com/alp82/curia/issues/11)) need exactly this per-spawn injection, and the auto-clear is the hygiene curia's ephemeral-cache posture wants.
4. **Stages as barrier groups.** `--stage N` groups sub-issues; the parent assignee is woken **once, when every sub-issue in the lowest unfinished stage reaches a terminal status** — a completion that doesn't close a stage is silent. This is a cheaper cousin of wayfinder's native blocking edges and a good model for how curia's overseer should be woken by a frontier advancing, rather than per-ticket.
5. **Deferred escalation with `fire_at`.** Route a comment to the mentioned agent; if unhandled, escalate to the assignee at `fire_at` (`migration 128`), cancelled automatically when the original task completes. A clean pattern for [#11](https://github.com/alp82/curia/issues/11)'s ~30-minute re-nudge and for orphaned-escalation cleanup.
6. **The `AskUserQuestion` rationale itself** (`claude.go:615-622`) — a second, independent party documenting that the tool silently returns an empty answer in headless stream-json mode. Worth citing in curia's own notes as external confirmation of the [#11](https://github.com/alp82/curia/issues/11)/[#23](https://github.com/alp82/curia/issues/23) MCP-tool choice, and a caution if any curia lane ever runs Claude headless without the MCP surface bound.
7. **Adapter arg allow/block lists.** Each backend defines which CLI flags user config may not override (`claudeBlockedArgs`, `--effort`/`--model`/`--output-format` locked to the daemon), with warn-and-drop on conflict. Cheap hardening for curia's [#13](https://github.com/alp82/curia/issues/13) routing when a per-ticket label and a per-agent default disagree.

## Open questions a hands-on spike would have to answer

None that change the verdict — the three filters fail at the level of absent code paths (no `issues` webhook case, no inbound WS message handler, no human-wait task state), which source-reading settles more cleanly than a boot would. If the destination ever moved so that Multica-as-tracker became acceptable, the open items would be: whether the published `ghcr.io` images bake a PostHog key; whether a per-agent `custom_env` can carry `CLAUDE_CONFIG_DIR` far enough to actually isolate the Claude lane despite no first-class support; and real footprint of daemon + N workers on an 8 GB box.
