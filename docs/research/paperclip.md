# Paperclip (paperclipai/paperclip, "Paperclip Labs, Inc.") — primary-source research

Date: 2026-07-24. Sources: repo `paperclipai/paperclip` cloned to scratch and read at commit **`d3c004d`** ("Fix issue descriptions in structured wake payloads (#10151)", 2026-07-24, `origin/master`); in-repo docs (`doc/`, `docs/`, `README.md`, `ROADMAP.md`, `DESIGN.md`); https://paperclip.ing and https://docs.paperclip.ing; npm registry (`paperclipai@2026.722.0` and the `@paperclipai/*` scope); GitHub API for stats. Vendor: "Paperclip Labs, Inc" (README `## License`); the LICENSE file says "Copyright (c) 2025 Paperclip AI".

**Verdict: (b) — a design reference, not grounds to reopen #17.** Paperclip is real, readable, MIT everywhere (repo *and* npm tarballs — no OpenACP-style split), and much better engineered than the marketing suggests: it spawns a **fresh subprocess per unit of work** (`spawn(...)` per run, `packages/adapter-utils/src/server-utils.ts:3132`), drives **real Claude Code over real ACP** (`@agentclientprotocol/claude-agent-acp` ^0.59.0 via openclaw's `acpx` 0.12.0), tears the process down after every turn by default (`DEFAULT_ACP_ENGINE_WARM_HANDLE_IDLE_MS = 0`), and hands the worker its ticket through env vars plus a `paperclip` skill that makes the worker call back over REST. That is curia's #9 model almost exactly. But it fails curia's decisive filter for the same reason hermes did, harder: **Paperclip's Postgres is the task list of record, by design and by roadmap.** There is no GitHub Issues ingestion — the only GitHub code in the repo is a read-only 300s-TTL *link status resolver* (`server/src/services/github-external-object-provider.ts`), and "Bring-your-own-ticket-system (Asana / Linear / Jira as on-ramps)" is an **unshipped ⚪ roadmap item** whose own framing is "Paperclip owns execution, governance, and outcomes" (`ROADMAP.md`). Adopting it means 158 Postgres tables and 189 migrations of authoritative local state next to GitHub — precisely the two-writer drift #9/#10 disqualified hermes' SQLite kanban for. It is also **zero** on curia's other two hard requirements: **no Discord, Telegram, or email exists anywhere in the codebase** (Slack exists only as an MCP tool an agent can call *outward*), and the live-run WebSocket has **no inbound message handler at all** — watching is multi-client, injecting is impossible. Worst, its headline feature is inert for curia's billing posture: budgets meter only `billed_cents`, and `normalizeBilledCostCents` returns **0 for `subscription_included`** (`server/src/services/heartbeat.ts:2681`), which is what Claude Code OAuth auth resolves to (`packages/adapters/claude-local/src/server/execute.ts:155-158`) — a Claude Max worker fleet would spend forever against a budget that never trips. What *is* worth stealing into #33 is concrete and named in §9.

## 1. What Paperclip actually is — verified

- **A single Node control plane over a Postgres org database, plus per-run agent subprocesses.** Stack (verified, `docs/start/architecture.md`, `Dockerfile`): React 19/Vite UI, Express 5 REST API, PostgreSQL 17 via Drizzle, adapters. The production Docker `CMD` is **one process** (`Dockerfile:92`) that serves the API, optionally serves the built UI (`SERVE_UI`, `server/src/config.ts:310`), runs embedded Postgres, and runs the heartbeat/routine loops in-process. There is no separate worker binary.
- **The unit of execution is a "heartbeat run."** Per `docs/start/architecture.md` "Request Flow": trigger → adapter `execute()` → **adapter spawns the agent (e.g. Claude Code CLI) with Paperclip env vars and a prompt** → the agent calls Paperclip's REST API to check assignments, checkout tasks, and update status → adapter parses usage/cost → server records the run. The worker-side protocol is a shipped skill, `skills/paperclip/SKILL.md`: *"You run in **heartbeats** — short execution windows triggered by Paperclip. Each heartbeat, you wake up, check your work, do something useful, and exit. You do not run continuously."*
- **"Agents" are DB rows, not processes.** `packages/db/src/schema/agents.ts` — `role`, `title`, `reportsTo` (self-FK = the org chart), `adapterType`, `adapterConfig` jsonb, `runtimeConfig` jsonb, `budgetMonthlyCents`, `spentMonthlyCents`, `pauseReason`, `permissions`. The org-chart/job-description framing is real and is stored, not simulated.
- **Adapter fleet is real and broad** (`packages/adapters/`): `claude-local`, `codex-local`, `cursor-local`, `cursor-cloud`, `gemini-local`, `grok-local`, `opencode-local`, `pi-local`, `hermes`, `hermes-gateway`, `openclaw-gateway`, plus generic `process` and `http` adapters in `server/src/adapters/`. The site's "unopinionated about agent runtimes" claim is **source-verified**, and broader than the site states (pi and OpenCode are in there too).
- **Marketing claims checked:** MIT — ✅ verified (§8). Self-hostable — ✅ verified (§8). Org chart / roles / reporting lines — ✅ verified (`agents.reportsTo`). Monthly per-agent budgets with hard stop — ✅ mechanism verified, but see §7 for the condition under which it does nothing. Full tool-call tracing and audit log — ✅ verified (`activityLog`, `toolCallEvents`, `toolAccessAuditEvents`, `heartbeatRunEvents`). Pause/terminate any agent — ✅ verified (`agents.status`/`pauseReason`, budget service pauses and cancels scope work). **"No sales call, no waitlist, no usage meter phoning home"** (paperclip.ing/product/open-source/) — ❌ **contradicted by source**: first-party telemetry is **enabled by default** (`server/src/config.ts:335` `telemetryEnabled: … ?? true`) and POSTs to `https://telemetry.paperclip.ing/ingest` with an AWS API Gateway fallback (`packages/shared/src/telemetry/client.ts:14-16`). The README is honest about this ("Telemetry is **enabled by default**", opt out via `PAPERCLIP_TELEMETRY_DISABLED=1` / `DO_NOT_TRACK=1`); the marketing page is not.

## 2. Role fit (dispatcher) — a real dispatch loop, and it *does* spawn fresh per unit of work

- **There is a genuine dispatch loop.** One `setInterval` in `server/src/index.ts:1018-1169`, default **30s** (`server/src/config.ts:87`, floor 10s, `HEARTBEAT_SCHEDULER_INTERVAL_MS`), enabled unless `HEARTBEAT_SCHEDULER_ENABLED=false`. Each tick runs `tickTimers` (per-agent elapsed-interval wake, `heartbeat.ts:17070-17139`), `routines.tickScheduledTriggers` (real 5-field cron, hand-rolled parser in `server/src/services/cron.ts`, no `node-cron` dep), plus a full reconciliation sweep (orphan reaping, stranded-issue reconcile, stale-lock sweep, watchdogs).
- **It is a queue with claim/lease and caps, not just a poller.** `startNextQueuedRunForAgent` (`heartbeat.ts:11759-11850`) computes `availableSlots = maxConcurrentRuns - runningCount`, prioritizes queued runs by dependency-readiness / issue status / priority / age, then `claimQueuedRun` (`heartbeat.ts:10714-10813`) **re-validates at claim time** — invokability, budget block, daily run and cost caps, tree holds, dependency blockers, staleness — before the run is actually claimed. Statuses: `queued | scheduled_retry | running | succeeded | interrupted | failed | cancelled | timed_out` (`packages/shared/src/constants.ts:834`).
- **Triggers**: `timer | assignment | on_demand | automation` (`server/src/services/issue-assignment-wakeup.ts:4`), plus routine cron, plus **signed inbound webhooks** — `POST /routine-triggers/public/:publicId/fire` accepts `x-paperclip-signature` **or GitHub-compatible `x-hub-signature-256` HMAC** (`server/src/routes/routines.ts:656-667`, `services/routines.ts:2796`), and plugin webhooks at `POST /api/plugins/:pluginId/webhooks/:endpointKey`.
- **Fresh worker per unit of work — confirmed, this is the default.** `packages/adapter-utils/src/server-utils.ts:3132` does `spawn(target.command, target.args, { cwd, env: childEnv, detached: true, shell: false, … })` per run. For the ACP lane, `packages/adapter-utils/src/acpx-engine/constants.ts:6` sets `DEFAULT_ACP_ENGINE_WARM_HANDLE_IDLE_MS = 0`, and with `warmIdleMs = 0` the keep-warm branch is never taken — the `else` fires `runtime.close({ reason: "paperclip completed turn cleanup" })` (`acpx-engine/execute.ts:2860-2875`). Standing processes exist only as an explicitly configured, idle-bounded optimisation (`warmHandleIdleMs > 0`) and are **never** used on the remote/sandbox lane (`acpx-engine/execute.ts:141-145`: *"torn down each run and resumed via `session/load`"*).
- **Caveat on the standing-vs-fresh framing**: the *process* is fresh, but the *identity* is a standing agent row, and the *conversation* is resumed across runs by ACP session id keyed `paperclip:companyId:agentId:taskKey:fingerprint`. So a Paperclip worker is "same employee, new shift, same memory" — closer to curia's #9 than to hermes, but not identical to curia's clean-slate-per-ticket posture.
- **Weakness:** the per-agent start lock is an **in-process `Map` mutex** with a 30s stale timeout (`server/src/services/agent-start-lock.ts:4,32-48`) — no Postgres advisory lock, no Redis. Single-server semantics only. Fine for a Hetzner box; not a distributed dispatcher.

## 3. State home — the decisive filter, and Paperclip fails it

- **Paperclip owns 158 Postgres tables.** Counted from `packages/db/src/schema/*.ts` (68 files). Authoritative task state is `issues` (`packages/db/src/schema/issues.ts`: status, workMode, priority, `assigneeAgentId`, `checkoutRunId`, `executionLockedAt`, `assigneeAdapterOverrides`, `executionPolicy`, `unblockDescriptor`, …), driven by `heartbeatRuns` and `agentWakeupRequests`. Plus org chart, budgets, approvals, activity log, tool-access audit, pipelines/cases, plugins, secrets, skills store.
- **Postgres is mandatory.** `packages/db/drizzle.config.ts:6` `dialect: "postgresql"`. No SQLite anywhere. "Embedded Postgres" means the **real** `embedded-postgres` npm package (`packages/db/package.json`, `^18.1.0-beta.16`) shipping an actual `postgres` server binary — not PGlite/WASM (there is no `@electric-sql/pglite` dependency; the string `"pglite"` survives only as a legacy config-mode name silently migrated to `"embedded-postgres"` in `packages/db/src/runtime-config.ts:114-130`; `docs/start/architecture.md` and `doc/DOCKER.md:54` are both stale on this).
- **It does not ingest an external tracker's frontier. At all.** No `octokit`, no GitHub App, no issue importer, no polling sync, no `routes/github.ts` / `linear.ts` / `jira.ts`. The GitHub code that exists (`server/src/services/github-external-object-provider.ts`) resolves a `github.com/**/issues/N` or `/pull/N` URL mentioned inside a Paperclip task into a cached status snapshot (open/closed/merged/draft, `GITHUB_OBJECT_TTL_SECONDS = 300`) so a Paperclip task can be shown as blocked on a PR. It **never creates or updates a Paperclip issue from a GitHub issue**. Linear exists only as an outbound MCP tool definition (`packages/shared/src/app-definitions/linear.json` → `https://mcp.linear.app/mcp`). Jira does not exist.
- **The roadmap says this is deliberate.** `ROADMAP.md`, unshipped (⚪): *"Bring-your-own-ticket-system (Asana / Linear / Jira as on-ramps) — Existing ticket systems should be able to feed work into Paperclip without becoming the agent control plane themselves… while **Paperclip owns execution, governance, and outcomes.**"* GitHub is not even on that list. "Work Queues" is also ⚪ unshipped.
- **Consequence for curia:** the best available integration is "GitHub webhook → signed routine trigger → Paperclip creates its own `issue` row assigned to a Paperclip agent" (`dispatchRoutineRun` requires an `assigneeAgentId`, `routines.ts:1630-1634`). That is a **mirror**, i.e. exactly the two-writer drift #9/#10 rejected — now with 158 tables and 189 migrations of it instead of hermes' one SQLite kanban. There is no configuration in which GitHub stays the single source of truth and Paperclip is a driven component.

## 4. Worker lane — the strongest part, and genuinely useful reading

- **Real ACP, real Claude Code.** `packages/adapters/claude-local/package.json` depends on `@agentclientprotocol/claude-agent-acp` ^0.59.0; the engine is openclaw's **`acpx` 0.12.0** (`packages/adapter-utils/package.json`; npm: MIT, `git+https://github.com/openclaw/acpx.git`, "Headless CLI client for the Agent Client Protocol"). `packages/adapters/claude-local/src/server/acp.ts:375-380` resolves the `claude-agent-acp` binary from the package, then PATH, then `node_modules/.bin`. Engine select is `auto | cli | acp`, **defaulting to ACP with documented fallback to the Claude CLI** (`config-schema.ts`, `resolveClaudeExecutionEngineForRun`). Codex has the parallel lane (`@agentclientprotocol/codex-acp` in `paperclipai`'s deps). This is not an LLM-loop abstraction — hermes' failure mode is absent.
- **Per-spawn env surface: yes, real.** `config.env` is an adapter config map merged into the child env (`claude-local/src/server/execute.ts:206`, `:288-296`), with `PAPERCLIP_*` runtime keys protected and `PAPERCLIP_API_KEY` never accepted from config. Base env is `{ ...process.env, ...env }` (`execute.ts:303-307`).
- **Per-worker `CLAUDE_CONFIG_DIR` (curia #29): expressible, but not the default — and the default is the failure mode curia flagged.** `hasExplicitClaudeConfigDir` is read from `config.env.CLAUDE_CONFIG_DIR` (`execute.ts:445`) and honored; otherwise `resolveSharedClaudeConfigDir` falls back to the **server process's own** `CLAUDE_CONFIG_DIR` or `~/.claude` (`claude-config.ts:115-120`) — i.e. host-config inheritance by default. Under the local sandbox path it is explicitly pinned to the *shared* dir (`execute.ts:549`: `if (filesystemScope) env.CLAUDE_CONFIG_DIR = sharedClaudeConfigDir`). Paperclip *does* maintain per-company/per-agent state dirs (`resolveManagedClaudeRuntimeStateDir(env, companyId, agentId)` → `<instanceRoot>/companies/<c>/agents/<a>/claude-runtime`, `claude-config.ts:136-147`) but uses them for MCP config and run artifacts, and only materializes a per-agent Claude home on the **remote/managed** execution target (`prepareClaudeConfigSeed` + `materializeRemoteClaudeConfig`, which seeds `settings.json`/`CLAUDE.md` and copies `.credentials.json`). Verdict: curia's hard requirement is satisfiable **as configuration**, not as a guarantee.
- **Per-run config override exists.** `issues.assigneeAdapterOverrides` = `{ modelProfile, adapterConfig, useProjectWorkspace }` (`heartbeat.ts:2937-2957`), and `mergeModelProfileAdapterConfig` shallow-merges `issueAdapterConfig` over the agent's base config at run time (`heartbeat.ts:2500-2505`, applied at `:12345-12348`). So `model` and `env` **are** settable per task. (`modelProfile` itself is a one-value enum today: `MODEL_PROFILE_KEYS = ["cheap"]`, `packages/shared/src/constants.ts:95`.)
- **Wake context is handed over as env + JSON, not as a conversation.** `PAPERCLIP_RUN_ID`, `PAPERCLIP_TASK_ID`, `PAPERCLIP_WAKE_REASON`, `PAPERCLIP_WAKE_COMMENT_ID`, `PAPERCLIP_APPROVAL_ID`/`_STATUS`, `PAPERCLIP_LINKED_ISSUE_IDS`, `PAPERCLIP_ISSUE_WORK_MODE`, and **`PAPERCLIP_WAKE_PAYLOAD_JSON`** — a bounded JSON blob with the issue summary and the ordered batch of new comments (`execute.ts:206-258`; built by `buildPaperclipWakePayload`, `heartbeat.ts:4398+`; the HEAD commit `d3c004d` is a fix to it). The same pattern is used by all ten CLI adapters.
- **ACP permission default is `approve-all`** (`acpx-engine/constants.ts:4`). Tool-call governance is not done at the ACP permission layer; it is done at Paperclip's MCP gateway (§5).

## 5. Escalation (HITL) — durable, but a different shape than curia's, and with no chat surface

- **The primitive exists and is fully durable in Postgres.** `issue_thread_interactions` (`packages/db/src/schema/issue_thread_interactions.ts:13-54`) with kinds `ask_user_questions`, `request_confirmation`, `request_item_verdicts`, `suggest_tasks`; fields `status`, `continuationPolicy` (default `wake_assignee`), `payload`/`result` jsonb, `sourceRunId` FK. Human answers via `POST /issues/:id/interactions/:id/respond` (`server/src/routes/issues.ts:9464-9508`), which inserts an `agentWakeupRequests` row (`heartbeat.ts:15224-15265`) scheduling a **new** run.
- **But it is not a blocking ask — it is "end your turn and get re-woken."** `server/src/services/tool-gateway.ts:1464` instructs the agent verbatim: *"Do not retry this call now. Wrap up other work and end your run noting you are waiting on tool approval… You will be woken when it is decided."* The tool-approval path is the same shape: HTTP 409 `approval_required`, agent exits, retries the identical call with `approvedActionRequestId` on a later run (`doc/MCP-ACCESS-GOVERNANCE.md:294-296`). MCP `elicitation` is mapped onto the same interaction table (`tool-gateway.ts:2896-2969`).
- **Restart survival: trivially yes, because nothing is in memory.** Pending interactions and approvals are rows; on boot `server/src/index.ts:918-1005` runs `reconcileHotRestartAdoption()`, `reapOrphanedRuns()`, `promoteDueScheduledRetries`, `resumeQueuedRuns()`, and the liveness reconcilers, and `server/src/services/recovery/issue-graph-liveness.ts:359-409` explicitly treats pending interactions/approvals as a legitimate "waiting" state so the recovery scanner does not false-positive on them. This clears curia's #22/#31 bar by construction — it is stricter than OpenACP's in-memory pending map, and comparable in spirit to curia's append-only journal.
- **Discord: does not exist.** No `discord.js`/`discord.py` dependency in any `package.json`; no bundled app definition; the only hits are an unused `discord.bot_token` secret-name placeholder (`packages/shared/src/constants.ts:715-733`) and a maintainer-workflow skill that drafts a release announcement for a human to paste into the project's own community server. Telegram: **zero hits repo-wide**. Email/SMTP: no `nodemailer`/`sendgrid`/`mailgun`/`postmark`/`twilio` anywhere. Slack exists only as an MCP catalog entry (`packages/shared/src/app-definitions/slack.json` → `https://mcp.slack.com/mcp`) — an *outbound tool an agent may be granted*, not wired to any escalation or notification path.
- **Therefore: the web console is the only human channel.** Humans are notified through in-app attention/inbox/badge services (`server/src/services/attention.ts`, `sidebar-badges.ts`) over the live-events WebSocket. There is no push to any external surface. For curia this is a total miss on the phone-escalation requirement — and curia's #31 Discord bridge is already built and verified live.

## 6. Attach — read-only, confirmed by absence

- **Realtime layer:** WebSocket at `/api/companies/:companyId/events/ws` (`server/src/realtime/live-events-ws.ts`), a thin bridge over an **in-process** `node:events` emitter keyed by `companyId` (`server/src/services/live-events.ts:7,46-49`) — not Redis, so multi-instance deployments see only their own instance's events. Event types (`packages/shared/src/constants.ts:856-869`): `heartbeat.run.queued/status/progress/event/log`, `agent.status`, `activity.logged`, `external_object.updated`, plugin events.
- **Multi-client watching: yes.** Company-scoped fan-out; every tab/device gets an independent subscription to identical events, filtered client-side by `runId` (`ui/src/components/transcript/useLiveRunTranscripts.ts`).
- **Injecting into a live turn: impossible.** `live-events-ws.ts:223-252` registers only `pong`/`close`/`error` handlers — **there is no `socket.on("message", …)` at all**; the server never parses inbound frames. Repo-wide search for `interject`/`steer`/`nudge`/`inject` returns zero matches in real code. Posting a comment mid-turn does not reach the running process; it lands as a row and wakes the agent's *next* run (`issue-assignment-wakeup.ts`, comment-wake coalescing at `routes/issues.ts:10262-10484`).
- **There is a real bidirectional PTY over WebSocket** — `server/src/realtime/environment-custom-image-terminal-ws.ts` (ssh2-backed, `input`/`output`/`resize` frames) — but it is gated to a custom-image **setup session** in status `waiting_for_user`. It has nothing to do with attaching to a live agent turn. Curia's #12 filter (concurrent multi-client input into one canonical timeline) is not met; #30's tmux+ttyd substrate is strictly more capable here.

## 7. Routing and budgets

- **Model per spawn: yes, via `issues.assigneeAdapterOverrides.adapterConfig`** shallow-merged over the agent's `adapterConfig` at run time (§4). A `model:<x>` label → `{ adapterConfig: { model: "…" } }` mapping is a direct fit, and is the single most transferable schema idea in the repo.
- **Budget mechanism, in source** (`server/src/services/budgets.ts`, tables `budgetPolicies`, `budgetIncidents`, `costEvents`, `approvals`):
  - A policy is `{ scopeType: company|agent|project, scopeId, metric, windowKind: calendar_month_utc|lifetime, amount, warnPercent (default 80), hardStopEnabled, notifyEnabled, isActive }`.
  - **Accounting unit is dollars, not tokens**: `BUDGET_METRICS = ["billed_cents"]` — a one-value enum (`packages/shared/src/constants.ts:793`), and `computeObservedAmount` returns 0 for any other metric (`budgets.ts:147`). Observed spend = `SUM(costEvents.costCents)` scoped to agent/project and windowed to the UTC calendar month.
  - **Who meters: the adapter, from the runtime's own report.** `claude-local/src/server/parse.ts:105-106` reads `total_cost_usd` off the Claude CLI's final result event (plus a per-model usage ledger for input/cached/output tokens). The server converts with `normalizeBilledCostCents` (`heartbeat.ts:2679-2683`).
  - **Two enforcement points, both correct in shape.** Post-hoc: `evaluateCostEvent` runs on every recorded cost event → at `warnPercent` opens a soft `budgetIncident`; at 100% opens a hard incident, **creates a pending `approvals` row of type `budget_override_required`**, sets `agents.status = paused` / `pauseReason = "budget"`, and calls `hooks.cancelWorkForScope` to kill queued work. Pre-flight: `getInvocationBlock(companyId, agentId, {projectId})` is consulted before starting new work and blocks at company → agent → project scope with a human-readable reason. Recovery is an explicit operator action: `resolveIncident({action: "raise_budget_and_resume", amount})`, which refuses any new amount ≤ current observed spend (`budgets.ts:884-886`).
- **The hard stop is inert on subscription auth.** `resolveClaudeBillingType` returns `"subscription"` whenever `ANTHROPIC_API_KEY` is unset (`claude-local/src/server/execute.ts:155-158`), i.e. normal Claude Code OAuth / Max. `normalizeBilledCostCents` then returns **0** for `subscription_included` (`heartbeat.ts:2681`). Tokens are still recorded on `costEvents` (`inputTokens`/`cachedInputTokens`/`outputTokens`, and the costs service breaks out `subscriptionRunCount` and subscription token sums) — but **no budget metric can read them**. So "monthly budgets per agent that hard-stop" is true only for metered API keys or Bedrock. Curia should judge it on that basis: the *mechanism* is worth stealing, the *metric* is not.
- **Quota handling — the most directly relevant code in the repo, and it goes the opposite way from curia's #13.** Paperclip is **proactive**: `packages/adapters/claude-local/src/server/quota.ts` reads the OAuth access token out of `<claude config dir>/.credentials.json` and GETs the undocumented **`https://api.anthropic.com/api/oauth/usage`** with header `anthropic-beta: oauth-2025-04-20`, returning `five_hour`, `seven_day`, `seven_day_sonnet`, `seven_day_opus`, and `extra_usage` windows each with `utilization` and `resets_at` — with a PTY-scrape of the `claude` `/usage` panel as fallback. It *also* has the reactive half curia designed: `parse.ts:13-19` carries three regexes matching `claude usage limit reached` / `5-hour limit reached` / `weekly limit reached` / `session limit reached` / `out of extra usage` / 429 / 529 / `throttlingexception`, including a capture group that extracts the **`resets at <time>`** clause. Both halves are readable, tested (`quota-windows.test.ts`), and MIT.

## 8. Maturity / license / self-host

- **Stats (GitHub API, 2026-07-24):** 74,659 stars, 13,904 forks, 4,917 open issues, TypeScript, ~142 MB. Repo created **2026-03-02** — five months old. Pushed today; **429 commits in the last 30 days**.
- **Bus factor: essentially 1.** 177 contributor pages (`anon=1`), but `cryppadotta` has 2,295 commits vs. the #2 contributor's 272 and #3's 89 (dependabot). This is a one-author core with a long tail, backed by a company (Paperclip Labs, Inc.) but not by a lab-scale team.
- **Cadence:** calver releases every 1-3 weeks — `v2026.722.0` (2026-07-22), `v2026.720.0`, `v2026.707.0`, `v2026.626.0`, `v2026.618.0`, …
- **License: MIT, verified on both sides — no split.** Repo `LICENSE` is MIT ("Copyright (c) 2025 Paperclip AI"); GitHub API `spdx_id: MIT`. Downloaded and inspected the published tarballs for `paperclipai@2026.722.0`, `@paperclipai/server@2026.722.0`, and `@paperclipai/adapter-claude-local@2026.722.0`: each ships `package/LICENSE` containing the same MIT text with `"license": "MIT"` in `package.json`. Actively evolving, not a stable v1.
- **External deps:** no Redis, no broker. S3 optional (`PAPERCLIP_STORAGE_PROVIDER`, default `local_disk`). OpenTelemetry optional and off. Telemetry on by default and phoning home (§1).

## 9. Verdict

**(b) — a design reference for the daemon, worth borrowing into #33. Not grounds to reopen #17, and not out of scope.**

Reopening #17 would require discarding or rebuilding, at minimum: curia's GitHub-as-single-source-of-truth ruling (#9/#10) — replaced by a 158-table Postgres mirror plus a GitHub→webhook→`issues`-row sync layer curia would have to write itself, since none ships; the entire #31 Discord bridge and durable escalation journal, already built and verified live, since Paperclip has no chat surface of any kind and its console is the only human channel; and the #30 tmux+ttyd attach substrate, since Paperclip's live-run WebSocket is provably one-way. The one thing a reopen would *buy* — a working dispatch loop — is the part curia has already scoped as thin-custom, and Paperclip's version is a 30s `setInterval` with an in-process `Map` mutex, i.e. not obviously beyond what #33 will produce. That trade is not close.

**Specific borrowable mechanisms for #33:**

1. **Wake-payload-by-env-var + a worker-side skill contract.** `PAPERCLIP_WAKE_PAYLOAD_JSON` (bounded issue summary + ordered new-comment batch + a `fallbackFetchNeeded` flag) plus the "scoped-wake fast path" in `skills/paperclip/SKILL.md` (*"skip Steps 1–4 entirely… do NOT fetch your inbox, do NOT pick work"*) is a clean answer to "how much context does a freshly spawned worker get for free vs. fetch." Curia already passes ticket binding on the spawn URL (#11); this is the next layer.
2. **Claim-time re-validation.** `claimQueuedRun` re-checks invokability, caps, holds, and blockers *at the moment of claim*, not at enqueue. Cheap to copy, prevents a stale queue entry spawning a worker that should not exist.
3. **Hot-restart process adoption.** `server/src/services/hot-restart.ts` writes a `hot-restart-intent.json` with the prior PID and a per-run pid/process-group snapshot, so a restarted daemon **adopts** still-alive children rather than orphaning them (`adopted | finalized_while_down | lost | skipped`). curia's daemon journal currently accepts losing the in-process worker call on restart (`daemon/README.md`); this is the pattern that would fix it.
4. **Per-task adapter-config override, as a schema shape.** `issues.assigneeAdapterOverrides.adapterConfig` shallow-merged over the agent's base config at spawn is exactly the shape #13's `model:<x>` label needs, generalized to arbitrary keys (including `env`).
5. **The quota code, both halves, MIT.** The three usage-limit regexes with the `resets at` capture group (`claude-local/src/server/parse.ts:13-19`) are a ready-made implementation of curia's reactive cooldown trigger — copy the patterns, skip the polling. Separately, the `https://api.anthropic.com/api/oauth/usage` endpoint with `anthropic-beta: oauth-2025-04-20` is a documented-in-source, zero-token way to read the 5-hour / 7-day / per-model windows and their `resets_at` — worth knowing exists even though #13 rejected polling.
6. **Budget shape, not budget metric.** Policy → soft incident at `warnPercent` → hard incident + pending approval + pause scope + cancel queued work, with a pre-flight `getInvocationBlock` gate and a resume path that refuses an amount ≤ observed spend. Worth stealing if curia ever runs metered API keys. **Do not steal `billed_cents` as the metric** — it is 0 under subscription auth, which is curia's posture; a curia equivalent would have to meter tokens or wall-clock runs.
7. **Escalation-as-end-turn (a contrast, not a copy).** Paperclip's HITL is "exit the run, wake later with `PAPERCLIP_APPROVAL_ID` set" rather than curia's blocking MCP `ask_human`. It is strictly more restart-durable and strictly worse for latency and for a live attached human. Worth recording in #22/#31 as the road not taken, with the reason.

## Open questions a hands-on spike would have to answer

*(Only relevant if the verdict is ever revisited — none of these block treating Paperclip as a reference.)*

1. **Does the `assigneeAdapterOverrides.adapterConfig.env` path actually reach the child env end to end**, i.e. can a per-task `CLAUDE_CONFIG_DIR` be set from the issue row alone? Source says yes (merge at `heartbeat.ts:2505` → `execute.ts:288-296`) but the `hasExplicitClaudeConfigDir` gate and the `filesystemScope` override at `execute.ts:549` interact in ways only a live run settles.
2. **Real memory footprint** of one Node process running the API + embedded Postgres 18 + heartbeat loops on a 2 GB Hetzner box, under, say, three concurrent Claude Code ACP children. The docs claim 1 vCPU / 2 GB; nothing measures it.
3. **`warmHandleIdleMs = 0` behaviour under load** — confirm the ACP child really is torn down each turn (and that `session/load` resume works from a cold process) rather than leaking handles.
4. **Whether the routine public-trigger webhook can be driven by a GitHub Actions/webhook payload** end to end with `x-hub-signature-256`, and what the resulting `issues` row looks like — this is the only path by which GitHub could feed Paperclip, and the fidelity of that mapping determines how bad the drift would be.
5. **Quota probe reliability**: does `api.anthropic.com/api/oauth/usage` still respond with that beta header, and does the `/usage` PTY-scrape fallback work headless? (Independently useful for #13 regardless of Paperclip.)
6. **Multi-writer safety**: the per-agent start lock is an in-process `Map`. What actually happens if two server processes point at one Postgres? Nothing in source suggests it is safe.
