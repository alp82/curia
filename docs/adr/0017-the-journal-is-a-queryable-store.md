# ADR-0017: The journal is a queryable store

**Status**: accepted (2026-08). The write path, the schema and the migration are built, by [#407](https://github.com/alp82/curia/issues/407). The rest of the build is charted on [the journal map (#316)](https://github.com/alp82/curia/issues/316).
**Provenance**: [The journal becomes a queryable store (#303)](https://github.com/alp82/curia/issues/303), [Where does the truth live (#319)](https://github.com/alp82/curia/issues/319)

## Context

[ADR-0001](0001-github-is-the-only-durable-state-home.md) named `daemon/data/events.jsonl` curia's one durable artifact. It is append-only text, one JSON object per line, and it never rotates. The operator ruled at the [#303](https://github.com/alp82/curia/issues/303) escalation that the journal becomes a `node:sqlite` store. That ruling left one question open, and this record answers it: does the store hold the truth, or do the lines hold it while the store serves as a derived index?

The evidence is measured. [What the journal scans cost](../research/journal-scan-cost.md) holds the full table.

- Ten `#readJournal` call sites ask **fourteen** distinct questions. More than thirty callers sit above them.
- All fourteen take one of three shapes. The last event of a type for a key. Whether a type occurred for a key after that key's epoch. One count. Not one is an ad-hoc query over history.
- One whole read costs about **25 ms** today. The read dominates the question by about twenty to one.
- The box held **4,282 events in 1.4 MB** on 2026-08-13, and it grows about **404 events per day**.
- `#epochScan` runs at the end of every turn of every agent. It reaches a quarter of a second per turn in about five months.

[What `node:sqlite` guarantees](../research/node-sqlite-guarantees.md) holds the durability facts. Node 24.19 marks the module Stability 1.2, which stays experimental. A Node patch update can change the API, the defaults, and the bundled SQLite engine.

## Decision

- **The journal holds the truth.** The `node:sqlite` database is curia's durable artifact. `daemon/data/events.jsonl` has retired. **Applied by [#407](https://github.com/alp82/curia/issues/407)**: `daemon/src/journal.mjs` holds the schema, the writer and the migration.
- **A row keeps the written line verbatim.** A `body` column holds the exact text curia serialized. The other columns are extracted copies, and they exist for indexing. So the store is a superset of the file, and a query regenerates that file byte for byte.
- **The daemon owns the only write connection.** Every other process opens the store read-only. WAL permits one writer, and every process must sit on one host.
- **The store runs WAL with `synchronous=FULL`.** The store now holds the record, so a commit lost to a power cut is a record lost. FULL costs about 1.230 ms per insert, against about 404 events per day.
- **A periodic `.dump` backs up the store, and the Node patch version is pinned.** The record sits on an experimental module, and curia does not carry that risk bare. `sqlite3 events.db .dump` produces portable SQL text. **Settled by [#357](https://github.com/alp82/curia/issues/357)**: the daemon takes a daily dump and keeps fourteen, and one Node patch version pins every curia image. The consequences below hold the parameters.
- **The old spelling survives untouched.** [#184](https://github.com/alp82/curia/issues/184) renamed the worker to the agent, and the journal was never rewritten to match. Curia stores the line as written and translates on read, exactly as `normalizeEvent` does today.

## Considered options

**The lines stay the truth, and the store is a derived index rebuilt at boot.** This was the recommendation this ticket opened with, and the operator moved off it. It puts no record on an experimental module, and a bad Node upgrade costs only a rebuild. It keeps `grep` and `tail -f` free.

It was refused for three reasons. It needs a dual write and a divergence window, because a process can die between the append and the insert. It keeps a boot cost proportional to the whole history. It leaves the text file growing forever, because the journal never rotates.

Two arguments made for it did not survive. The smaller migration is a migration argument, and the operator accepts a migration. The cheaper write path is real as a ratio and not as a number, because 404 events per day at 1.230 ms costs about half a second per day.

**One general index in the store, about 150 lines.** It answers all fourteen questions with no migration and no write-path change, and the journal stays a text file. It answers nothing outside the three shapes. The operator put it up at the #303 escalation and turned it down, which reads as buying the query engine rather than the ten scans.

## Consequences

- **ADR-0001's journal bullet moves here.** That record now points at this one.
- **ADR-0001's "no local brain to lose" gains a caveat.** Restart recovery is still a re-query against GitHub, and the tracker still holds ticket state. The store is a local brain, and the `.dump` is what bounds the loss. **Settled by [#357](https://github.com/alp82/curia/issues/357)**: the dump is daily, so the loss is bounded at one day.
- **The daemon takes its own backup, and it stays on the box.** **Settled by [#357](https://github.com/alp82/curia/issues/357)**. The daemon spawns `sqlite3 events.db .dump` on a second read-only connection, gzips the SQL text, and writes `daemon/data/backups/events-<UTC stamp>.sql.gz`. It checks at boot and every hour, and it dumps when the newest dump is 24 hours old or older. A plain 24-hour timer is wrong here, because a deploy restarts the daemon and rearms that timer. Curia keeps the newest fourteen dumps and deletes the rest. That is about 250 KB per dump and about 3.5 MB in total, at the volume the box wrote on 2026-08-13. The dump bounds a corrupt journal and a bad Node upgrade. It does not survive the loss of the box, and an off-box copy is a separate effort.
- **A restore is a hand recipe, and never a verb.** **Settled by [#357](https://github.com/alp82/curia/issues/357)**. A restore is rare and destructive, and a human picks which dump. So curia ships no verb and no button for it, and [the daemon README](../../daemon/README.md#the-restore) holds the steps.
- **The daemon says when its backup stops.** **Settled by [#357](https://github.com/alp82/curia/issues/357)**. A failed dump journals and reaches the channel. A newest dump over 48 hours old journals and reaches the channel too. So silence never stands in for a timer that failed to arm. A success journals one event and says nothing, so an ordinary day carries no noise. The dashboard shows none of this, because its container does not mount `daemon/data`.
- **One Node patch version pins every curia image, in two committed places, with no default.** **Settled by [#357](https://github.com/alp82/curia/issues/357)**. `deploy/compose.yaml` passes `NODE_VERSION` to the daemon, the dashboard and the overseer from one anchor. `config/curia.yaml` gains `sandbox.node_version` for the agent image, beside the other pins, so a bump rides the image content address and the daemon rebuilds. The three Dockerfile `ARG NODE_VERSION` defaults go, and a build that forgets the arg then fails. That is the rule the agent Dockerfile already states. `daemon/package.json` gains `engines.node` as a warning and not a wall, because a daemon that refuses to install is worse than the stack trace it prevents. The agent image joins the set on purpose: it ran `FROM node:lts-slim` and served Node 24.19.0 while the daemon ran 22.17.1, and the daemon suite runs in that image. So the suite that must prove an upgrade ran on a Node nobody pinned. **Applied by [#409](https://github.com/alp82/curia/issues/409)**: the first value is Node 24.19.0, the version the schema prototype and the guarantees research both ran on, and all four Dockerfiles now name the distro as well.
- **A Node upgrade passes three gates before it reaches the box.** **Settled by [#357](https://github.com/alp82/curia/issues/357)**. First the daemon suite is green on the new pin. Then two read-only commands run against the box's live `events.db` under the new daemon image: `pragma integrity_check`, and one of the fourteen queries. The suite builds a fresh database, so it cannot catch an engine that refuses the existing file. Last comes the self-deploy health check, which already resets the box. The daemon journals `process.version` and `process.versions.sqlite` at boot, so the journal states which engine wrote its rows. Curia bumps Node only for a reason: a Node security release that touches what curia runs, or a `node:sqlite` fix curia needs. A calendar bump is a floating pin with extra steps. [The daemon README](../../daemon/README.md#the-node-pin) holds the recipe.
- **The operator queries the store, and curia builds nothing to help.** [#320](https://github.com/alp82/curia/issues/320) decided the surface: a read-only `sqlite3` shell out of the daemon image, and no wrapper, no text tail, and no backwards compatibility with the old `grep` pipelines. The store exists to make a question cheap, so the answer to a question is a query. That decision puts one requirement on the schema: extract the columns a human types by hand, and normalize the [#184](https://github.com/alp82/curia/issues/184) spelling into them. `sqlite3` joined the daemon image with the Node bump, at [#409](https://github.com/alp82/curia/issues/409). The queries are in [the daemon README](../../daemon/README.md#reading-the-journal).
- **Retention becomes possible and stays undecided.** The text file never rotated. A row deletes. Nothing here rules on what curia keeps. That open question is about rows. It is not the fourteen dumps above, which are a backup count. One constraint is already known: the boot rebuild runs over the whole history, so a deleted row changes the reduction. `consoleSpent` holds every console conversation key ever minted and must never shrink ([#333](https://github.com/alp82/curia/issues/333)). Delete the oldest `console_conversation_opened` rows and a spent number can be minted again, which wakes a deleted conversation's memory.
- **The schema is not decided here.** [#321](https://github.com/alp82/curia/issues/321) prototypes it against the fourteen queries. This record fixes only the verbatim `body` column and the truth.
- **The scans become queries.** The dispatcher read the whole journal at ten call sites, and this record's whole case is that a question should cost the question. **Applied by [#408](https://github.com/alp82/curia/issues/408)**: `daemon/src/questions.mjs` holds them, and `Reduction#journalEvents` is gone, so nothing hands out the whole journal any more. Every `(ticket or agent)` test is two `exists`, because one disjunction drops both keyed indexes. The three questions the Stop hook asks cost about 0.08 ms together at 60,000 events, where one read and one scan cost 258 ms, and they stay flat. The queries were checked against the dispatcher's own loop over 43,386 comparisons at that size, with no mismatch. The count is fifteen and not fourteen. `#reconcileStaleQuestions` ([#336](https://github.com/alp82/curia/issues/336)) landed after the research measured the file, and it read the same whole journal.
- **The boot rebuild survives, and it reads the journal.** `EscalationStore._replay` read the whole file once per process and filled every [#289](https://github.com/alp82/curia/issues/289) reduction from that one pass. [#322](https://github.com/alp82/curia/issues/322) ruled that the rebuild stays. Three reductions keep rows verbatim and could be queries, and every other field folds many rows into an object no row holds. The reducer must also run on every append, so a query at boot would state each rule twice. The rebuild reads `select id, body from events where id > ? order by id limit 1000`, page by page. It orders by `id` and never by `ts`, because stamps tie. It reads `body`, so it is the last reader that runs `normalizeEvent`. `EscalationStore._replay` is now `Reduction#rebuild`, because "replay" already names sending a killed turn's message again. **Applied by [#407](https://github.com/alp82/curia/issues/407)**.
- **The boot cost stays proportional to the whole history, and the medium does not move it.** [The boot rebuild prototype](../../prototypes/boot-replay/README.md) measured 43.9 ms from the file against 42.1 ms from the journal at the live size, and 2,369 ms against 2,569 ms at 250,000 events. Reading is about a third of a boot, `JSON.parse` is about another third, and the reducer is the rest. Narrowing the scan to the 32 types the reducer acts on wins 18 ms today and ties at 250,000 events, so #322 refused it. A snapshot of the reduction was refused too: the reduction is a disposable cache, and a snapshot makes a reducer bug permanent.
- **The existing file migrates, and it stays on disk.** **Settled by [#323](https://github.com/alp82/curia/issues/323)** and **applied by [#407](https://github.com/alp82/curia/issues/407)**: the daemon converts at first boot. It finds `events.db` absent, reads the journal file whole, inserts every line in one transaction, and renames the database into place after the row count matches the line count. The measured cost is 298 ms for 4,282 events. The file is not renamed and not deleted, because the self-deploy rollback has no human in it and the previous daemon looks for that exact path. [#427](https://github.com/alp82/curia/issues/427) deletes it once the journal is checked on the box. [The daemon README](../../daemon/README.md#the-migration-to-the-database) holds the rollback recipe.
- **The write path changes at every `logEvent` call site**, and the crash guard must still journal while the process dies. `installCrashGuard` journals and then exits, and a synchronous insert completes before that exit. **Applied by [#407](https://github.com/alp82/curia/issues/407)**: `logEvent` is now `Reduction#journal`, and the insert is synchronous.
- **The test suite changes.** 37 places across 14 test files seeded or read `events.jsonl` directly. **Applied by [#407](https://github.com/alp82/curia/issues/407)**: a test that seeds the journal file still works, because the migration converts it. A test that reads back what the daemon wrote reads the journal.
- **The word "store" named two things.** `EscalationStore` lived in `daemon/src/store.mjs` and held the in-memory reductions. The durable artifact above is also a store. Curia writes one name for one thing, so the build picks a second name before it writes code. **Settled by [#358](https://github.com/alp82/curia/issues/358)**: "store" names nothing in curia. The durable record keeps the name **journal**, whatever medium holds it, so the `node:sqlite` database IS the journal. The in-memory state is the **reduction**, and `EscalationStore` became `Reduction` in `daemon/src/reduction.mjs` at [#407](https://github.com/alp82/curia/issues/407). `CONTEXT.md` holds the vocabulary.
