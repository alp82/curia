# ADR-0006: Agent containment and standing orders

**Status**: accepted (2026-07), amended 2026-08 (#155, #159, #180, #172, #161, #268)
**Provenance**: [Build preview-link allocation (#40)](https://github.com/alp82/curia/issues/40), [Close the loop: the agent resolves its ticket (#41)](https://github.com/alp82/curia/issues/41), [Align the agent's standing orders with the wayfinder skill (#49)](https://github.com/alp82/curia/issues/49), [Mint the scoped GitHub PAT and inject GH_TOKEN (#155)](https://github.com/alp82/curia/issues/155), [Per-agent token on the daemon loopback (#159)](https://github.com/alp82/curia/issues/159), [An agent reaches the operator's account connectors (#180)](https://github.com/alp82/curia/issues/180), [A codex agent carries an apps namespace curia never configured (#172)](https://github.com/alp82/curia/issues/172), [Route-gap duty in the agent skill (#161)](https://github.com/alp82/curia/issues/161), [Matt's skills move to 1.2 (#268)](https://github.com/alp82/curia/issues/268)

## Context

A dispatched agent holds `gh` and full read access, so its authority must be shaped, not assumed. The full-loop rehearsal exposed agents that rebuilt tools they already had, resolved before review, and never advanced the map.

## Decision

- The agent resolves its ticket in the tracker's own idiom with `gh`: resolution comment, close, one map pointer. The daemon verifies at `report_result` and repairs what is missing, marked as repairs.
- The daemon lands the code: it pushes `curia/<n>` and opens the one pull request. Agents never push. The base clone's push URL stays disabled.
- Standing orders supply parameters and bounds, not procedure. Procedure lives in the skill set curia installs into every agent's config dir, so an agent resolves in the same idiom as a hand session. Since [#268](https://github.com/alp82/curia/issues/268) that set is vendored in this repo.
- Read is unbounded. The agent may zoom any issue, map, or closed ticket. Writes are bounded: the worktree, the ticket, the map subtree, nothing else on the tracker, and the assignee stays untouched.
- The agent has no browser and must not build one. The orders name the daemon's tools with one-line reach-for-it-when lines, because a tool manifest alone loses to a strong prior.
- The agent carries full charting authority, human-gated: fog graduation, new tickets, blocking edges, scope rulings. The proposal must be concrete in the gate text, or the approval is a rubber stamp.
- Preview ports are daemon-allocated. The registry refuses curia's own surfaces and requires a live listener, because "publish this port" is a privileged request.
- The evidence rule governs every read: a failed read is not evidence. Only a positive absent narrows a set. Every uncertain case fails toward keeping work.
- Bounds are standing orders, not controls, and the docs say so plainly.
- **Amended by [#155](https://github.com/alp82/curia/issues/155)**: the tracker half of "nothing else on the tracker" is now a control, not only an order. An agent reaches GitHub with a scoped fine-grained PAT as `GH_TOKEN` — one per resource owner, Contents/Issues/Pull requests read-write plus Commit statuses read — instead of the host's account-wide `gh` login. Read stays unbounded within those repos. Everything the token does not name is refused by GitHub rather than by a standing order.
- **Amended by [#159](https://github.com/alp82/curia/issues/159)**: an agent's own NAME is a control too. `/mcp` and `/agent_done` take the agent's name in a query param, and until #159 that name was the whole claim — anything that reached the daemon port could report a result for another agent, ask a question as it, or end its turn. The daemon now mints a secret per agent at spawn and delivers it in the connection settings (a header on the MCP server, the same header on the Stop hook's curl), refusing any call whose token does not match the name it claims. The container-facing listener carries those two routes and nothing else, so a container reaches neither `/command` nor `/answer`. The token is a header rather than an environment variable because a pane env rides tmux argv and lands in `ps`, which is the cost #155 measured.

- **Amended by [#340](https://github.com/alp82/curia/issues/340)**: the orders move OUT of the spawn prompt. They rode one user message, and #340 measured what that costs from the codex CLI's own rollout: codex keeps `AGENTS.md`, the environment and the skill catalog as world state and restates them. A user message is conversation. Its instructions then tell the model that the last user request is current and every earlier one is stale, and that a skill binds only the turn that named it. A wayfinder ticket is many turns, so the bounds and the ending were a stale first message by the end of one. The orders now ride the CLI's global-memory file in the config dir, `CLAUDE.md` or `AGENTS.md`, which each CLI loads as instructions rather than as a turn. The spawn prompt keeps what its name always claimed: the parameters of this dispatch, plus one line pointing at the orders. The file is a row in the harness table, so a new lane must name its own or carry no durable orders at all. Nothing about the split reaches the skill. It is upstream's bytes, it loads on turn one, and #49's ruling stands: install it, do not restate it.

- **Amended by [#180](https://github.com/alp82/curia/issues/180)**: an agent's TOOL SET is a control too, and it was never bounded. `CLAUDE_CONFIG_DIR` holds the #23/#29 line for every MCP server named in a config file. The operator's account-level claude.ai connectors are not named in one. Claude Code fetches them over the wire from the account behind the credential, which [ADR-0007](0007-shared-credential-store.md) shares with the host on purpose, so an agent listed 38 tools where curia configured six and could read and write the operator's Notion, Gmail, Drive and Calendar. The bound is two settings keys in the config dir curia already owns: `disableClaudeAiConnectors` stops the fetch, ahead of every auth branch in the CLI's own eligibility chain, and `allowedMcpServers` admits curia's server and nothing else whatever route another one arrives by. Neither touches the credential. The sandbox ([ADR-0012](0012-one-container-per-worker.md)) does not reach this at all: a connector call is ordinary outbound HTTPS, and the network is open by design.

- **Amended by [#172](https://github.com/alp82/curia/issues/172)**: #180 bounded the tool set on ONE harness. Codex carried the same fault under another name, and the mechanism rhymes: the `codex_apps` namespace follows the ChatGPT credential rather than any config file, and [ADR-0007](0007-shared-credential-store.md) shares that credential with the host on purpose. A live codex agent held plugin search, install and uninstall, plus `_update_app_permissions`, `resume_agent` and `close_agent`. None of it was in `[mcp_servers]`, and none of it was in the bounds. The bound is three lines in the `[features]` table curia already writes for `hooks`: `apps`, `plugins` and `multi_agent`, every one of them `stable` and defaulting to true. The trap is the OPPOSITE shape to #180's, and both halves were induced: a key codex does not know is ignored in SILENCE, so a rename upstream fails as a no-op that reads like a bound lane. A key with the wrong type is a hard error that stops the spawn loudly. So nothing here can take curia's own server down, and the guard has to be a live read of the effective state rather than a unit test on the written string ([docs/live-checks/172](../live-checks/172-codex-apps-namespace.md)). One thing no setting on either harness reaches: a skill that installs an MCP server, a `codex plugin add`, a `claude mcp add`. That half is a standing order, and the spawn prompt now carries it harness-blind. The tools are the ones curia configured, and the set is closed.

- **Amended by [#161](https://github.com/alp82/curia/issues/161)**: the agent reading a map cold is a standing order too. [#149](https://github.com/alp82/curia/issues/149) ruled out a verification gate on a freshly charted map, so nothing behind the charting model and the human in that loop checks whether the map can reach its destination. The dispatched agent is the only fresh pair of eyes left, and curia-107 proved the catch works by finding exactly that gap on the landing-page map — by luck, not by duty. So a mapped ticket dispatch now carries one order: a map that stops short of its destination goes in the agent's FIRST `ask_human` call, not into a workaround and not into the review gate. It rides the spawn prompt rather than the wayfinder skill, because the skill is a host file outside this repo, it loads on claude only ([#173](https://github.com/alp82/curia/issues/173)), and it has no word for "escalation" — a hand session has the human in the room. Charting dispatches are exempt: changing the map is already their job.

- **Amended by [#268](https://github.com/alp82/curia/issues/268)**: the procedure half was never in this repo, and that was a hole in the same shape as #180's. The skill set is the procedure an agent obeys, and it lived at `~/.agents/skills` on the operator's box, reached through `~/.claude/skills`. So it sat outside every write bound, outside the review gate and outside version control at once: nobody could read an upgrade as a diff, and the `prototype` skill had drifted from its release with no record of who changed it or why. The bound is the ordinary one for a dependency — **vendor it**. The 25 promoted skills are copied into `skills/` at the repo root under upstream's MIT license, `skills.root` names `../skills` relative to the config, and `skills/UPSTREAM.md` pins the release and commit. A skill upgrade is now a pull request the gate reads. This is what makes an upgrade *checkable*: version 1.2 turns `grilling` from one question at a time into a numbered round, which contradicts [ADR-0005](0005-escalation-contract.md), and under the old arrangement that change would have arrived silently on the next update. `skills.install` still bounds what an agent gets, so vendoring the whole promoted set widens the tree and not the agent. The one install method that stays refused is the Claude Code plugin: it lands under `<config dir>/plugins/`, which `installSkills` never reads, and two installs leave every skill twice.

## Consequences

- The daemon cannot verify the charting half. The review gate is the only control on it, and — since #161 — the next agent dispatched under the map.
- Concurrent map writes converge agent-side by read, modify, write, re-read, redo. The daemon's map lock covers only its own repair writes.
- Every ticket type dispatches, HITL included, so HITL agents are the long-lived slot tenants.
- The one merge exception to "agents never push" is defined in [ADR-0008](0008-resolved-means-merged.md).
