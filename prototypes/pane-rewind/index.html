alp82/curia#542

The pane-driven rewind

Can curia drive each harness's own rewind with keystrokes in the pane? This demo holds the evidence of live probes: a real CLI in a tmux pane, every keystroke sent through the daemon's own paced write path (daemon/src/tmux.mjs), and the result read from the disk and from the wire. The Discord receipt and the dashboard composer are static mocks (sections 6 and 7). Decided ground: ADR-0021.

1 The rig

Each probe spawns the real CLI in a detached tmux session, exactly as curia dispatches an agent. The driver (drive.mjs) imports newSession, sendText and sendKey from daemon/src/tmux.mjs, so the pacing and the paste-fold guard are the production ones. claude ran a real model with the container credential. codex ran against a scripted stand-in on the Responses wire API (standin-codex.mjs), the pattern of docs/research/pane-keystroke-codex.probe.mjs. opencode and pi ran against a chat-completions twin (standin-chat.mjs), installed pinned after the operator's approval. A stand-in scripts every turn, so the conversation cut is read off the request body and never off a model's report of itself. Every turn wrote a file through the harness's own tool, so the file question has an answer on disk.

8 The verdict

The button shows only where a lane passes, and every lane passes. Two lanes restore files with the conversation (claude, opencode). Two restore the conversation only (codex, pi), and there the receipt says the tree stands. Every lane prefills its composer with the taken-back text, and curia clears it — Ctrl+C on claude, Ctrl+U on the other three — so the text waits in the receipt and the dashboard composer, never in the pane.
