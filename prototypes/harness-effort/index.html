How each harness takes a reasoning effort

Four lanes, one question each: where does the effort enter, which words does the lane accept, where does it read back, how does a wrong value fail, and can it change on a resume. Every claim is read off a live run's request body, captured by a stand-in model server. The pane never judges itself.

The rig claude codex opencode pi Summary

1 The rig

Each probe spawns the real CLI in a detached tmux pane through drive.mjs, the daemon's own paced write path. The CLI talks to a local stand-in model server (standin-anthropic.mjs, standin-responses.mjs, standin-chat.mjs) that logs every request whole. So the effort a spawn states is proven on the wire, and the pane captures show only where a human can read it back. Raw captures sit in evidence/.

2 claude 2.1.220 PROVEN

A spawn flag, five levels, a per-turn transcript record, and a warning instead of a refusal. The wire field is output_config.effort on POST /v1/messages.

  • Mechanism: claude --effort xhigh at spawn. The env var CLAUDE_CODE_EFFORT_LEVEL works too (req-18 sent low off the env var alone). A settings.json key named effort does nothing (req-16).
  • Vocabulary: low medium high xhigh max — the daemon's union minus ultra, one to one. Hidden extra: --effort ultracode is accepted and rides the wire as xhigh (req-14).
  • Default: high, proven by the no-flag resume (req-8) and the invalid-value fallback (req-12).
  • Mid-session: the /effort slider. The next turn sends the new value (req-6). The switch is session-only: a bare --continue falls back to high (req-8), and --continue --effort low wins (req-10). So an override applies on every spawn, resume included.

3 codex 0.146.0 PROVEN

The known config key, a seventh word, and two traps: garbage passes through, and ultra lies on the readback. The wire field is reasoning.effort on POST /v1/responses.

  • Mechanism: model_reasoning_effort in config.toml (what workspace.mjs writes today), or per spawn as -c model_reasoning_effort="x".
  • Vocabulary: minimal low medium high xhigh max ultra. The picker names Max and Ultra "Advanced Reasoning · consumes usage limits faster", Ultra "for demanding work using multiple agents". minimal sits below the union's floor. ultra matches the union by name — but see the trap.
  • Default: per model, not one constant. The picker marks Low as the default for gpt-5.6-sol. routing.yaml already records gpt-5.5 defaulting to medium.
  • Mid-session: the /model picker switches effort per session (req-11) and never writes config.toml.

  • Readback: footer gpt-5.6-sol low · ~/ws, exec header reasoning effort: …, and the rollout's turn_context payloads — all echo the CONFIGURED string, wrong values included. The daemon already parses rollouts, so per-turn effort is readable, with the ultra caveat.
