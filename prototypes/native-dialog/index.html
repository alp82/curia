The native dialog on the chat page

A native menu — the harness question picker, the trust prompt — holds the terminal pane, and the chat page cannot show it. Today the page pins an amber guard banner and refuses every send. This demo shows the web copy: the page reads the menu from the pane text, draws it as a card, and answers it with keystrokes. Every pane below is a live capture of the real TUI, and every keystroke plan was proven against the real harness (findings.md).

The decision


Does the web copy replace the dialog guard banner?



  
card
    
When the pane parses, the card replaces the banner body. The menu the
    operator must answer is drawn in the chat, in the escalation card's own language, and a tap
    answers it. The terminal link stays in the card header — the pane is still one click away.

  
banner
    
When detection fires and the parse fails, the banner stays. The scrolled
    fixture shows it live: a menu the pane clips down to one entry refuses to parse, and the
    guard banner with the terminal link is exactly what #515 decided. The banner is the fallback,
    never deleted.

  
veto
    
The send veto stays. A composer send still returns 409 while any dialog
    owns the pane. The card's own keystrokes are the one sanctioned writer, so a stale phone and a
    mid-answer race stay refused — the #75 containment is unchanged.

  
seam
    
The parse runs daemon-side. The daemon already probes the pane on the
    watchdog cadence; the parsed menu rides the existing SSE dialog event as a structured payload,
    and a tap posts back an option index the daemon turns into keys. The page never touches tmux,
    and the pane stays untrusted text handled by one parser with unit fixtures.
